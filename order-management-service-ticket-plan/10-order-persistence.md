# Ticket 10 — Order Persistence and Order Number

## Objective
Persist submitted orders and their exact calculation snapshot.

## Technical Design

### orders
Store:
- id
- orderNumber
- quantity
- destination latitude
- destination longitude
- subtotalCents
- discountRate
- discountCents
- amountAfterDiscountCents
- shippingCents
- totalCents
- currency
- status
- createdAt

### order_allocations
Store:
- orderId
- warehouseId
- quantity
- distanceKm
- shippingCents

## Snapshot Principle
Historical orders must not be recalculated using future pricing rules.

Persist the calculated values at submission time.

## Order Number
Must be:
- generated by server
- unique
- safe under concurrent creation

A database sequence/UUID-backed identifier can support uniqueness while a human-readable order number is exposed.

## Acceptance Criteria
- Order and allocations persist.
- Order number is unique.
- Pricing snapshot is preserved.
- Historical order does not depend on current pricing rules.

## Test Cases
- Create order.
- Create multi-warehouse allocation.
- Concurrent order-number generation.
- Retrieve persisted snapshot.

## Dependencies
Ticket 03.

## Definition of Done
Migration/schema, repository, and persistence tests are complete.
